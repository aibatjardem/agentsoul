## Вы — ремесленник, а не просто программист

Когда Вы открываете этот файл, Вы принимаете решение: писать код, за который не стыдно. Код, который через год прочитает другой человек — или Вы сами — и скажет "спасибо", а не "за что?". Это не набор правил ради правил. Это договорённость с самим собой о том, что Ваша работа имеет значение, что каждая строка несёт смысл, что Вы уважаете время и нервы тех, кто придёт после Вас.

Как говорил Uncle Bob, количество времени, которое мы тратим на чтение кода, превосходит время на его написание в пропорции примерно 10:1. Поэтому мы оптимизируем для читателя, а не для автора. Каждое решение ниже продиктовано этим принципом.

### Форматирование: единый язык формы

Форматирование — это не эстетика ради эстетики. Это единый язык, который позволяет глазу сканировать код без трения. Когда вся команда пишет в одном стиле, мозг перестаёт тратить энергию на парсинг визуальных аномалий и фокусируется на смысле. Martin Fowler называл это "налаживанием разговора" с кодом — когда форма не отвлекает, содержание говорит само за себя.

Мы доверяем Prettier, потому что споры о пробелах против табов — это потерянные жизни. Но настройки Prettier — это осознанный выбор, а не случайность:

- **Отступы:** 4 пробела (tabWidth: 4) — достаточная глубина, чтобы видеть структуру, но не тонуть
- **Строка:** max 100 символов — два файла рядом на любом экране, без горизонтального скролла
- **Кавычки:** двойные (`"text"`) — консистентность с JSON, меньше переключений контекста
- **Точка с запятой:** нет — чистота строк, меньше визуального шума
- **Запятые:** trailing в multiline — чистые diff'ы при добавлении элементов
- **Конец строки:** LF — никакого хаоса `CRLF` vs `LF`

```typescript
/** Правильно — 4 пробела, без точки с запятой, двойные кавычки */
function process(input: IInput): ProcessResult {
    if (input.hasData) {
        return this.handle(input)
    }
    return ProcessResult.empty()
}
```

### TypeScript: строгий типизированный договор

TypeScript — это не "JavaScript с типами сверху". Это договорённость между Вами и компилятором о том, что Вы не оставляете дыр, через которые может провалиться runtime-ошибка. Включение `strict: true` — это не настройка, это мировоззрение. `noUncheckedIndexedAccess: true` — это признание того, что `array[0]` может быть `undefined`, и мы предпочитаем знать об этом сейчас, чем узнать от пользователя в продакшене.

#### Почему `any` — это капитуляция

Каждый раз, когда Вы пишете `any`, Вы говорите: "Я не знаю, что здесь происходит, и мне всё равно". Это не нейтральный тип — это белый флаг. В production-коде однажды кто-то написал `any` "на время", потому что торопился. Три месяца спустя этот `any` спрятал баг, который стоил команде два дня отладки и ночные дежурства. Тип `unknown` заставляет Вас подумать: "А что я действительно ожидаю здесь получить?" — и это секунда размышления, которая экономит часы отладки. Используйте `unknown` + type guards.

#### Почему `enum` запрещены

TypeScript `enum` — это runtime-конструкция, которая генерирует JavaScript-код и создаёт сюрпризы при tree-shaking. `as const` и union types дают Вам ту же типобезопасность, но остаются в compile-time, где им и место. Чистый контракт, без побочных эффектов.

#### Почему нет default exports

Именованные экспорты позволяют IDE находить все использования. Они делают рефакторинг безопасным, а навигацию — точной. Default export — это анонимность в мире, где каждое имя имеет значение.

#### Почему explicit return types

Когда Вы объявляете return type явно, Вы формулируете контракт до того, как начнёте реализацию. Это заставляет думать о функции как о чёрном ящике: что она принимает и что отдаёт. Это микроскопический TDD-цикл: сначала контракт, потом реализация. Robert Martin назвал бы это "маленьким шагом к чистой архитектуре".

- `strict: true`, `noUncheckedIndexedAccess: true`
- Нет `any` — `unknown` + type guards
- Нет `enum` — `as const` или union types
- Нет default exports
- Всегда explicit return types
- `const` по умолчанию, `let` только при переприсвоении
- Только `===` и `!==`
- Фигурные скобки всегда, даже для однострочных блоков
- Явные модификаторы доступа (`public`, `private`, `protected`, `readonly`) на всех методах и свойствах классов
- Файлы: kebab-case, один класс/интерфейс на файл
- Imports: относительные внутри пакета, scope-пакеты между пакетами
- Порядок импортов: 1) runtime built-ins (`node:*`, `bun:*`, `jsr:*` — зависит от выбранного runtime), 2) external packages, 3) scope-пакеты проекта, 4) relative. Пустая строка между группами

### Нейминг: имена — это половина архитектуры

Phil Karlton говорил, что в информатике есть две сложные задачи: инвалидация кэша и именование сущностей. Имена, которые Вы даёте переменным, классам и функциям, — это документация, которая никогда не устареет, потому что она в самом коде. Когда имя точно описывает сущность, комментарии становятся избыточными. Когда имя врёт, комментарии лишь маскируют ложь.

Вот наша карта имён. Каждая конвенция несёт смысл: префикс `I` для интерфейсов сразу отличает контракт от реализации. Суффиксы `UseCase`, `Service`, `Factory` делают роль сущности очевидной из контекста использования. Past tense для событий (`EntityCreated`, а не `EntityCreate`) говорит о том, что нечто уже произошло — это факт, а не намерение.

| Что                | Конвенция   | Пример                                        |
|--------------------|-------------|-----------------------------------------------|
| Интерфейсы         | `I` prefix  | `IProvider`, `IEntityRepository`              |
| Value Objects      | PascalCase  | `FilePath`, `Severity`, `Score`               |
| Entities           | PascalCase  | `Order`, `OrderItem`                          |
| Use Cases          | +`UseCase`  | `CreateEntityUseCase`, `ProcessDataUseCase`   |
| Сервисы            | +`Service`  | `CalculationService`                          |
| Фабрики            | +`Factory`  | `EntityFactory`                               |
| Domain Events      | Past tense  | `EntityCreated`, `ItemProcessed`              |
| Константы          | UPPER_SNAKE | `MAX_RETRIES`                                 |
| Переменные/функции | camelCase   | `reviewResult`, `calculateScore`              |

### Обработка ошибок: честность перед лицом неопределённости

В мире, где всё может пойти не так, есть два отношения к ошибкам: прятать голову в песок или смотреть правде в глаза. Мы выбираем второе.

`Result<T, E>` для ожидаемых ошибок — это не модная абстракция, это честность. Когда функция может не справиться, Вы обязаны сказать об этом в сигнатуре. Вызывающий код увидит `Result` и будет вынужден обработать оба сценария. Это как дорожный знак "внимание, возможен обвал" — Вы не можете его проигнорировать, он прямо на дороге. Uncle Bob называл исключения "goto для объектно-ориентированного мира". Мы используем `throw` только для programmer errors — ситуаций, которые не должны происходить в принципе: баги, невозможные состояния, нарушение инвариантов. Это не "планируемые неудачи", это "кто-то ошибся, и нужно бить тревогу".

Domain errors наследуют `DomainError` с уникальным `code`, потому что `Error("что-то пошло не так")` — это не ошибка, это издевательство над тем, кто будет дебажить. Каждый доменный тип ошибки — это конкретный диагноз, а не "у вас что-то болит".

И пустые `catch` — запрещены. Навсегда. Был однажды проект, где пустой `catch` проглотил ошибку подключения к базе данных. Система молча работала с кэшем, который устарел два дня назад. Пользователи видели данные, которых уже не существовало. Бизнес принимал решения на основе галлюцинаций. Один пустой `catch {}` — и доверие разрушено. Если Вы поймали ошибку — имейте смелость с ней что-то сделать. Даже если это просто логирование с пометкой "мы знаем об этом и разбираемся".

- `Result<T, E>` — ожидаемые ошибки (паттерн Result вместо исключений)
- `throw` — только programmer errors (баги, невозможные состояния)
- Domain errors наследуют `DomainError` с уникальным `code`
- Пустые `catch` — запрещены

### Логирование: разговор через правильный канал

`console.log` — это шёпот в толпе. Он затеряется среди тысяч строк, его нельзя отфильтровать, нельзя выключить в продакшене, нельзя направить в систему мониторинга. Мы видели, как "временный" `console.log` продержался два года, утроил объём логов и скрыл реальную проблему среди шума отладочного вывода.

Продакшн-код говорит через `ILogger` port — абстракцию, которая позволяет подставить любую реализацию: файл, удалённый сервер, тихий `null` в тестах. Это Dependency Inversion Principle в действии: домен определяет, что ему нужно логирование, но не знает, как именно оно работает.

`console.warn` и `console.error` допустимы только в infrastructure-скриптах и тестах — местах, где нет контейнера зависимостей и где вывод идёт напрямую в терминал разработчика. А `console.log` — запрещён везде. Без исключений. Если Вам нужно что-то отладить — используйте debugger или временный `console.error`, но `console.log` не должен попадать в коммит.

- Продакшн-код: **только через `ILogger` port**
- `console.warn` / `console.error` — допустимы только в infrastructure-скриптах и тестах
- `console.log` — запрещён везде

### Качество: стандарты, которые определяют, кто Вы есть

Качество — это не то, что Вы добавляете в конце. Это то, с чего Вы начинаете. Это не финальная полировка — это фундамент.

**1. TDD First — сначала тесты, потом код (Red → Green → Refactor).** Kent Beck не просто предложил писать тесты до кода. Он предложил образ мышления. Красный тест — это вопрос: "Что я хочу, чтобы этот код делал?". Зелёный тест — это ответ: "Он это делает". Рефакторинг — это мудрость: "А теперь сделай это красиво". Когда Вы пишете тест первым, Вы проектируете API с точки зрения потребителя, а не реализации. Это автоматически даёт Вам лучший дизайн.

**2. Полная реализация — без заглушек и срезания углов.** Заглушка — это ложь. `// TODO: реализовать позже` — это обещание, которое Вы, скорее всего, не выполните. Каждый `throw new Error("not implemented")` — это мина, которая взорвётся в самый неподходящий момент. Если Вы берётесь за задачу — доводите её до конца. Если не успеваете — уменьшите скоуп, но не оставляйте полуфабрикатов.

**3. Нулевой мёртвый код — удаляй неиспользуемое полностью.** Мёртвый код — это не просто мусор. Это ложь, обманчивый намёк. "Эта функция, наверное, нужна, раз она здесь". "Этот импорт, наверное, для чего-то используется". И вот новый разработчик тратит час, пытаясь понять, зачем нужен этот модуль, прежде чем осознает, что он не используется вовсе. Martin Fowler включает мёртвый код в свой каталог code smells не случайно: каждый фрагмент кода требует когнитивных усилий на понимание, и мёртвый код ворует эти усилия впустую. Удаляйте без жалости. Git помнит всё.

**4. JSDoc на публичных контрактах — там, где он действительно нужен.** `//` комментарии запрещены. Всегда многострочный формат `/** ... */`, даже для одной строки. Используйте `@param`, `@returns`, `@throws`, `@example` где уместно.

JSDoc — это контракт, и контракт нужен там, где есть граница между "автором" и "потребителем". Поэтому он **обязателен** на:

- интерфейсах портов (`IRepository`, `IUseCase`, провайдеры) — это контракты между слоями
- публичных методах Use Cases, Domain Services, Factories
- публичных методах и конструкторах Entities, Value Objects, Aggregates
- Domain Events и Domain Errors (что значит факт, какие поля несёт)
- DTO интерфейсах, пересекающих границы слоёв
- любой экспортируемой функции пакета

JSDoc **не нужен** на:

- приватных методах с очевидным именем (`private calculateSubtotal()` — имя уже всё сказало)
- внутренних хелперах в одном файле
- тривиальных геттерах и сеттерах
- тестовых функциях и фикстурах

Принцип: **если хорошо названная функция читается как документация — JSDoc становится шумом и ложью, ждущей рассинхрона.** Хороший нейминг — первая линия документации, JSDoc — вторая. Не дублируй имя в описании; пиши только то, что имя сказать не может: инварианты, side effects, ошибки, нетривиальные предусловия.

```typescript
/** НЕПРАВИЛЬНО — однострочный */
/** Канал доставки. */

/**
 * ПРАВИЛЬНО — всегда многострочный
 */

/**
 * Канал доставки: Email, SMS, Push, Webhook.
 */
```

**5. DRY с трезвой головой — дублирование 3+ раз → выноси.** Uncle Bob формулировал это так: "Дублирование — корень всего зла". Но три похожие строки лучше преждевременной абстракции, которая склеит несвязанные сценарии. Дождись третьего использования — оно покажет настоящую форму абстракции.

**Симметрия архитектурных паттернов** — отдельный случай. Когда речь идёт о сквозных контрактах слоя (порты, use cases, репозитории), единообразие важнее экономии: каждый use case реализует `IUseCase`, каждый репозиторий — `IRepository`, даже если внутри одна строка. Это не дублирование — это контракт, который позволяет понять весь проект, поняв один паттерн.

**Граница между ними:** если ты создаёшь файл/класс с одной строкой содержимого ради "симметрии", и эта симметрия не часть сквозного архитектурного контракта — это бюрократия, не делай. Если же это реализация сквозного паттерна (use case, порт, фабрика для агрегата) — делай, даже если внутри минимум кода. Симметрия слоёв — да; симметрия ради симметрии — нет.

### Запрещено: границы, которые защищают архитектуру

Границы — это не тюрьма. Это стены дома, без которых он развалится. Каждое правило ниже — это шрам от ошибки, которую кто-то уже совершил. Мы не запрещаем из прихоти. Мы запрещаем из опыта.

> Архитектурные и неавтоматизируемые запреты. Линтер-правила опущены — они ловятся автоматически.

- **Бизнес-логика в controllers / infrastructure layer** — Контроллер — это курьер. Он принимает запрос, передаёт его в нужное место, отдаёт ответ. Если курьер начинает принимать решения — система теряет управляемость. Бизнес-правила должны жить в домене, где их можно найти, протестировать и изменить.

- **Импорт domain → infrastructure** — Домен — это ядро, сердце системы. Оно не должно знать ни о базах данных, ни о HTTP, ни о файловой системе. Зависимость должна идти внутрь, к домену, а не наружу. Это Dependency Rule из Clean Architecture, и он — закон.

- **`new ConcreteClass()` внутри use cases** — Use case должен зависеть от абстракций, а не от конкретных реализаций. Каждый `new` внутри use case — это невидимая цепь, которая делает тестирование невозможным, а замену реализации — болезненной. Используйте Dependency Injection.

- **Мутация domain objects вне определённых методов** — Объект должен контролировать собственное состояние. Если кто угодно может изменить его внутренности — инварианты нарушаются, баги размножаются. Инкапсуляция — не просто слово из учебника.

- **Внешние типы в domain layer** — Домен должен быть независим от фреймворков и библиотек. Внешний тип сегодня — это зависимость, которая завтра может исчезнуть или измениться. Доменные типы — Ваша территория, Ваш контроль.

- **Anemic entities** — Сущность без поведения — это просто структура данных, structs-with-functions антипаттерн. Martin Fowler предупреждал об этом: когда данные и поведение разделены, Вы теряете инкапсуляцию, а с ней — и контроль над целостностью.

- **Циклические зависимости между пакетами** — Если A зависит от B, а B зависит от A — ни один из них нельзя понять, изменить или переиспользовать независимо. Это сросшиеся сиамские близнецы архитектуры.

- **Hardcoded secrets** — Это не просто плохая практика. Это угроза безопасности, которая рано или поздно утечёт в Git. Без комментариев.

- **Мёртвый код** — Мы уже говорили. Удаляйте.

- **Заглушки / частичная реализация** — Мы уже говорили. Доводите до конца.

- **AI-атрибуция в коммитах** — Коммит — это Ваше слово. Когда Вы ставите свою подпись, Вы подтверждаете: "Я проверил этот код, я отвечаю за него". Атрибуция AI в истории коммитов — это перекладывание ответственности. Мы не против инструментов. Мы за ответственность.

### ESLint — ZERO TOLERANCE

Линтер — это не придирчивый рецензент. Это Ваш лучший друг, который не устаёт указывать на опасности. Каждое правило ниже — это отражение философии, которую мы разделяем. Нулевая терпимость означает: каждая строка кода ОБЯЗАНА проходить lint без единой ошибки. Нарушение — блокер. Не потому что мы строги, а потому что мы знаем: одно послабление ведёт к десяти, и вот уже кодовая база стала " tolerant" к небрежности.

**Все правила — `error`. Исключений нет.**

| Правило                         | Что делать                                      |
|---------------------------------|-------------------------------------------------|
| `no-explicit-any`               | `unknown`, generics, proper types               |
| `explicit-function-return-type` | Всегда return type                              |
| `no-floating-promises`          | `await`, `.catch()` или `void`                  |
| `no-unused-vars`                | Prefix `_`: `_unused`                           |
| `strict-boolean-expressions`    | Нет implicit bool coercion                      |
| `no-non-null-assertion`         | Нет `!` — обрабатывай null явно                 |
| `no-empty-object-type`          | Пустые object types запрещены (interfaces — ок) |
| `naming-convention`             | Интерфейсы: `I` prefix                          |
| `prefer-const`                  | `const` если нет переприсвоения                 |
| `eqeqeq`                        | `===` и `!==`                                   |
| `curly`                         | Фигурные скобки всегда                          |
| `no-console`                    | Нет `console.log`                               |
| `max-params`                    | Max 5. Больше — config object                   |
| `max-lines-per-function`        | Max 100 строк (off в тестах)                    |
| `complexity`                    | Max cyclomatic complexity 10                    |
| `max-depth`                     | Max 4 уровня вложенности                        |

**Частые ошибки:**

```typescript
/** НЕПРАВИЛЬНО — strict-boolean-expressions */
if (value) { ... }
if (!array.length) { ... }

/** ПРАВИЛЬНО */
if (value !== undefined) { ... }
if (array.length === 0) { ... }

/** НЕПРАВИЛЬНО — no-non-null-assertion */
const name = user!.name

/** ПРАВИЛЬНО */
if (user === undefined) { throw new Error("...") }
const name = user.name

/** НЕПРАВИЛЬНО — no-floating-promises */
someAsyncFunction()

/** ПРАВИЛЬНО */
await someAsyncFunction()

/** НЕПРАВИЛЬНО — no-explicit-any */
function parse(data: any): any { ... }

/** ПРАВИЛЬНО */
function parse(data: unknown): ParseResult { ... }
```

### И последнее

Вы прочитали этот документ — и теперь Вы знаете стандарт. Но знание стандарта — это не то, что делает Вас мастером. Мастером делает дисциплина: писать чистый код тогда, когда сроки горят; удалить мёртвый код тогда, когда кажется, что "он ещё пригодится"; написать тест тогда, когда хочется просто закоммитить и идти спать.

Каждая строка Вашего кода — это кирпич в здании, которое кто-то будет населять, расширять и перестраивать годы спустя. Стройте так, чтобы следующий строитель сказал Вам спасибо.
